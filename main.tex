\intro

Современное высшее образование, особенно в области информационных технологий, находится в условиях активной трансформации. Обусловлено это как нехваткой квалифицированных кадров на рынке труда, так и ростом числа желающих развиваться в IT индустрии. В таких условиях образовательные организации нуждаются в инструментах, обеспечивающих гибкость учебного процесса, удобное взаимодействие участников и практическую направленность обучения.

Одним из ключевых инструментов организации образовательного процесса являются системы управления обучением (Learning Management System, LMS). Такие системы автоматизируют администрирование учебных курсов, управление расписанием и успеваемостью, предоставляют средства коммуникации и совместной работы, а также обеспечивают удобные интерфейсы для сдачи и проверки практических заданий.

В то же время в индустрии информационных технологий для решения проблем версионирования, эффективного хранения проектов и организации совместной работы над ними широко применяются системы контроля версий (VCS), в частности Git. Освоение навыков работы с Git является одним из основных требований для будущих специалистов, поскольку этот инструмент является стандартом версионирования программного кода в современной разработке программного обеспечения. Интеграция Git в образовательный процесс, позволяющая студентам повседневно использовать его для сдачи и управления своими заданиями, способствует формированию профессиональных компетенций и облегчает их последующую адаптацию к требованиям рынка труда.

Целью данной работы является проектирование и реализация части образовательной платформы для IT"=специальностей, которая использует Git для версионирования студенческих заданий, а также обладает функционалом для удобной сдачи и проверки решений.

В ходе работы должны быть решены следующие задачи:
\begin{itemize}
	\item проанализировать существующие подходы к хранению программного кода, выявив преимущества системы контроля версий Git;
	\item изучить роль протокола SSH в передаче
	\item изучить функциональность протокола Git Wire;
	\item разработать механизм аутентификации и авторизации с использованием SSH"=ключей, а также управление доступом к репозиториям;
	\item спроектировать процесс взаимодействия студентов с подсистемой через CLI"=интерфейс и веб"=версию платформы и реализовать его;
	\item создать комбинированную модель хранения попыток, совмещающую Git для решений и реляционную базу данных для метаданных.
\end{itemize}

\section{Анализ предметной области}

\subsection{Архитектурный подход к интеграции Git}

Почти любая LMS это веб"=приложение. Студенты и преподаватели заходят через браузер, данные передаются по HTTP. Проблема в том, что Git не умеет работать через HTTP так, как это нужно для веб"=интерфейса. Его протокол Git Wire предполагает прямое соединение между клиентом и сервером, и традиционно он работает поверх SSH.

Для соединения веб"=приложения с Git используется архитектура, использующая два сервара --- dual"=protocol. Система разворачивает два сервера: один отвечает на HTTP"=запросы веб"=интерфейса, второй принимает Git"=соединения по SSH. При этом для разворачивания и взаимодействия используется общая кодовая база, которая просто разделяет свои домены.

На стороне Git"=сервера данные хранятся в bare"=репозиториях. Обычный репозиторий Git (тот, в котором работают разработчики) содержит рабочее дерево --- файлы в распакованном виде, которые можно открыть и отредактировать. Bare"=репозиторий устроен иначе: в нём нет рабочего дерева, только содержание Git --- объекты (blob, tree, commit), ссылки (ветки и теги), указатель HEAD и папка hooks со скриптами"=обработчиками. Файлы в нём лежат в сжатом виде, и править их напрямую нельзя. Именно bare"=репозитории используются на серверах, потому что они безопасны для одновременного приёма push"=запросов и не требуют синхронизации рабочего дерева \cite{chacon2014pro}.

Каждому заданию или студенту можно выделить отдельный bare"=репозиторий. Важно, чтобы путь к нему вычислялся детерминированно: если студент обращается к тому же заданию второй раз, он должен попасть в тот же репозиторий.

Стандартный Git"=сервер умеет принимать данные и записывать их в репозиторий. Но для образовательной платформы этого мало. Отправка решения не должна сводиться к записи файлов: нужно проверить, что студент сдаёт задания по порядку, зарегистрировать попытку в базе данных, обновить прогресс. Shell"=хуки для этого не подходят, так как они изолированы от приложения и не имеют доступа к его логике.

Решением является прослойка между SSH и Git. Такой подход называют middleware. Это промежуточный слой, который перехватывает запрос до того, как он попадёт к исполнителю. Middleware может проверить, кто обращается к серверу, выдать доступ, изменить запрос или завершить его с ошибкой.

Такой подход не влияет напрямую на работу Git --- он остается нетронутым, так как вся дополнительная логика находится в middleware, связывая Git с образовательной платформой.

\subsection{Сравнительный анализ подходов к хранению программного кода}
\label{sec:comparison}

Чтобы оценить, насколько тот или иной подход годится для хранения версионированного кода, нужна система координат. В теории баз данных для этого есть ACID --- набор свойств, которым должна удовлетворять надёжная система \cite{kleppmann}. Сам термин ввели Тео Хардер и Андреас Ройтер в 1983 году \cite{haerder1983principles}, опираясь на работы Джима Грея по транзакциям \cite{gray1981transaction}. ACID расшифровывается как:

\begin{itemize}
	\item Atomicity (атомарность) --- операция выполняется целиком или не выполняется вовсе;
	\item Consistency (согласованность) --- система всегда остаётся в корректном состоянии; инварианты не нарушаются;
	\item Isolation (изоляция) --- параллельные операции не влияют друг на друга;
	\item Durability (долговечность) --- если данные сохранены, они переживают сбой.
\end{itemize}

Разберем три подхода к хранению кода и рассмотрим, какие свойства из ACID в них присутствуют.

\subsubsection{Хранение файлов в реляционных СУБД (BLOB"=объекты)}

BLOB (Binary Large Object) --- тип данных в реляционных СУБД для хранения бинарных данных \cite{garcia2009database}. Если хранить код в BLOB, каждая попытка --- строка в таблице с полем типа BLOB.

Проблема в том, что реляционная модель не рассчитана на версионирование древовидных структур. BLOB --- чёрный ящик для базы данных: она не знает, что внутри, и не может гарантировать согласованность содержимого. Консистентность из ACID работает на уровне строки, но не на уровне структуры проекта \cite{postgresacid}.

Также, если задание состоит из нескольких файлов, нет атомарного обновления набора файлов как единого целого без дополнительной обвязки. Isolation могла бы давать изоляцию строк, но при конкурентной записи в BLOB возможны проблемы, описанные в документации PostgreSQL \cite{postgresacid}. Сравнение версий требует выгрузки BLOB"=ов наружу, для чего не располагает база данных.

BLOB решает задачу «просто сохранить байты», но не решает задачу «хранить версионированный код с историей».

\subsubsection{Хранение файлов на файловой системе}

Второй подход --- хранить каждую версию как набор файлов в директории на диске. Файловая система предоставляет базовые операции чтения и записи, но не является системой управления данными: в ней нет встроенных механизмов версионирования, атомарных групповых операций или средств контроля целостности.

Каждая операция записи работает с отдельным файлом, и если в процессе записи нескольких файлов произойдёт сбой, часть данных может быть потеряна, а согласованность директории --- нарушена. Также, после перезаписи файла предыдущее состояние становится недоступным, поэтому для реализации версионирования поверх файловой системы потребуется дополнительный слой, который будет отслеживать изменения и управлять копиями --- по сути, реализовывать функциональность, уже встроенную в Git.

\subsubsection{Хранение файлов с использованием Git}

Git --- это распределенная система контроля версий, созданная Линусом Торвальдсом в 2005 году для разработки ядра Linux.

В отличие от многих других систем, Git не хранит списки изменений между версиями. Вместо этого Git хранит полные слепки (snapshots) файлового дерева на каждый момент коммита. Такая схема хранения оказывается эффективнее за счет переиспользования неизмененных объектов.

В основе Git лежит \quot{контентно"=адресуемое хранилище}. Фактически Git --- это база данных «ключ --- значение», где ключом является SHA"=1 хеш содержимого, а значением --- сами данные \cite{aosagit}. Git использует четыре типа объектов:

\begin{itemize}
	\item Blob --- содержимое файла. У blob"=объекта нет имени файла, это просто набор байт. Если два разных файла имеют одинаковое содержимое, они будут ссылаться на один и тот же blob --- это позволяет избежать дублирования информации;
	\item Tree --- аналог директории. Содержит список записей вида \quot{имя файла --- ссылка на blob} или \quot{имя поддиректории --- ссылка на другой tree};
	\item Commit --- ссылается на корневой tree (полный слепок репозитория), на ноль или более родительских коммитов, а также хранит метаданные: автор, дата, сообщение	\item Tag --- именованная ссылка на коммит, обычно для обозначения версий.
\end{itemize}

Git позволяет экономить место на диске, так как при создании нового \quot{коммита}, он не копирует все файлы заново. Вместо этого он создает новые blob"=объекты только для измененных файлов. Файлы, которые не менялись, продолжают ссылаться на уже существующие объекты \cite{gitchaconobjects}.

Например, если в проекте из 100 файлов изменился один, Git создаст один новый blob, новый tree (для директории с измененным файлом) и новый commit. Остальные 99 файлов останутся на своих старых blob"=объектах.

Получается, что каждый коммит --- это полноценный снимок всего репозитория, но занимает он места ровно столько, сколько нужно, чтобы сохранить историю изменений.

Каждый объект в Git идентифицируется SHA"=1"=хешем, вычисленным на основе его содержимого. Если содержимое объекта изменится хотя бы на один байт, ранее вычисленный хеш уже не будет соответствовать этому содержимому, что позволит Git обнаружить повреждение.\cite{chacon2014pro}.

Коммиты в Git образуют направленный ациклический граф (DAG) \cite{aosagit}, в котором каждый коммит содержит ссылки на один или несколько родительских коммитов. Для организации параллельной разработки Git использует механизм веток. Ветка представляет собой указатель на последний коммит некоторой линии разработки. Благодаря тому, что ветки являются легковесными ссылками, их создание, переключение и удаление выполняются практически мгновенно, что упрощает ведение нескольких независимых направлений разработки.

Перечисленные свойства делают Git подходящей основой для подсистемы приёма студенческих решений. Также, поскольку каждый коммит --- полный слепок файлового дерева, diff между любыми двумя попытками вычисляется средствами Git без дополнительных усилий.

\subsection{Принципы работы протокола SSH}

SSH (Secure Shell) --- протокол безопасного удаленного доступа к серверам. Разработан в 1995 году финской компанией SSH Communications Security как замена небезопасным протоколам Telnet и rsh, которые передавали данные (включая пароли) в открытом виде \cite{rfc4251}.

SSH решает проблему общения компьютеров по незащищенному каналу (Интернет), причем так, чтобы никто не мог перехватить, прочитать или подменить передаваемые данные.

Архитектура SSH (RFC 4251) состоит из трех уровней и первый из них --- транспортный протокол (RFC 4253). Этот уровень работает поверх TCP и отвечает за установление защищенного соединения. Сначала сервер предъявляет свой host"=ключ --- клиент проверяет, что он подключился именно к тому серверу, к которому собирался. Затем стороны выполняют обмен ключами по протоколу Диффи"=Хеллмана, в результате которого получают общий секретный ключ. После этого весь трафик шифруется симметричным шифром (например, AES). Важная особенность --- \quot{perfect forward secrecy}: даже если злоумышленник когда"=нибудь узнает долговременный секретный ключ сервера, он не сможет расшифровать ранее перехваченные сессии \cite{rfc4253}.

После установки защищенного канала сервер проверяет подлинность клиента. Основные методы:
\begin{itemize}
	\item пароль --- классический способ, но пароль передаётся внутри защищённого канала;
	\item публичный ключ --- клиент доказывает, что владеет приватным ключом, соответствующим публичному ключу, который известен серверу;
	\item keyboard"=interactive --- сервер задаёт клиенту вопросы (например, одноразовый пароль из SMS).
\end{itemize}

Аутентификация по публичному ключу --- способ, удобный для автоматизированных сценариев. Пользователь генерирует пару ключей: приватный (хранится только у владельца) и публичный (можно свободно распространять), после чего публичный ключ добавляется на сервер. При подключении SSH использует криптографию с открытым ключом: сервер отправляет случайное число и просит подписать его приватным ключом. Если подпись верна --- клиент доказал, что владеет приватным ключом, и аутентификация проходит успешно.

После аутентификации протокол соединения мультиплексирует несколько логических каналов внутри одного SSH"=соединения. Через одно соединение можно одновременно передавать файлы, запускать несколько команд, пересылать порты.

Для использования SSH с Git можно реализовать собственный SSH"=сервер, который будет принимать подключения, проверять аутентификацию по ключам и выполнять нужные команды. Это дает возможность интегрировать аутентификацию с произвольным хранилищем данных --- например, проверять ключи через базу данных, а не через системные файлы authorized\_keys. Такой подход упрощает управление ключами и позволяет реализовать механизмы добавления и удаления ключей через API.

\subsection{Протокол Git Wire и его функционирование}
\label{sec:gitwire}

Когда разработчик выполняет \texttt{git push} или \texttt{git pull}, Git"=клиент и Git"=сервер обмениваются данными по определенному протоколу --- Git Wire Protocol \cite{gitprotocolpack}. Этот протокол определяет, как клиент и сервер договариваются о том, какие данные нужно передать,     и как эти данные упаковываются в pack"=файлы.

В основе протокола Git Wire лежит pkt"=line формат --- каждая строка данных начинается с четырёх шестнадцатеричных цифр, которые задают длину сообщения (и включают собственную длину). Строка \texttt{0000} обозначает конец списка, а \texttt{0001} --- конец сообщения \cite{gitprotocolpack}. В этом формате проходит вся стадия переговоров клиента с сервером, в рамках которой стороны договариваются о составе передаваемых данных. Сами же данные передаются в виде pack"=файла --- бинарного формата, в котором объекты Git (коммиты, деревья, blob"=объекты) упакованы с дельта"=сжатием для эффективной передачи по сети \cite{gitprotocolpack}.

В Git существует два основных сценария передачи данных.

В первом случае клиент хочет получить данные с сервера. Пользователь выполняет \texttt{git clone ssh://user@example.com/project.git} или \texttt{git fetch}, что внутри Git преобразуется в SSH"=вызов: \texttt{ssh user@example.com "git-upload-pack '/project.git'"}. На сервере запускается процесс \path{git-upload-pack} \cite{gitprotocolpack}. Последовательность шагов:
\begin{enumerate}
	\item Клиент подключается к серверу и запрашивает \texttt{git-upload-pack}.
	\item Сервер отправляет список ссылок (refs): какие ветки существуют и на какие коммиты они указывают.
	\item Клиент сообщает серверу, какие коммиты у него уже есть.
	\item Сервер вычисляет, каких объектов не хватает клиенту, упаковывает их в pack"=файл и отправляет.
\end{enumerate}

Во втором случае клиент хочет отправить данные на сервер. Пользователь выполняет \texttt{git push}. Git формирует SSH"=вызов: \texttt{ssh user@example.com "git-receive-pack '/project.git'"}:
\begin{enumerate}
	\item Клиент подключается к серверу и запрашивает \texttt{git-receive-pack}.
	\item Сервер отправляет текущие ссылки.
	\item Клиент сообщает, какие ссылки он хочет обновить и какие новые объекты (коммиты, blob"=ы) для этого нужны.
	\item Сервер проверяет, можно ли выполнить обновление.
	\item Клиент упаковывает новые объекты в pack"=файл и отправляет.
	\item Перед обновлением ссылок Git запускает pre"=receive хуки. Если хук завершается с ненулевым кодом, операция отклоняется целиком \cite{githooks}.
	\item Сервер принимает данные и обновляет ссылки.
	\item После успешного обновления ссылок выполняются post"=receive хуки \cite{githooks}.
\end{enumerate}

После запуска процесса Git"=клиент и Git"=сервер общаются напрямую через stdin/stdout, а SSH обеспечивает шифрование и аутентификацию.

Git предоставляет механизм хуков (как упомяналось выше, при работе команды \path{git} \path{push}) --- shell"=скриптов, которые автоматически вызываются в определённые моменты жизненного цикла операции \cite{githooks}. В контексте приёма данных на сервере используются два хука:

\begin{itemize}
	\item pre"=receive --- выполняется после получения всех данных (pack"=файлов в том числе) от клиента, до обновления ссылок репозитория. Ненулевой код возврата программы хука отклоняет операцию целиком, загруженные данные позже удаляются;
	\item post"=receive --- выполняется после успешного обновления ссылок.
\end{itemize}

Полезная в узкоспециализированных случаях возможность Git"=протокола --- push"=опции. Они позволяют передавать произвольные строковые параметры вместе с операцией \texttt{git push} через флаг \texttt{-o} или \texttt{--push-option} \cite{gitprotocolpack}. Для передачи push"=опций сервер должен включить соответствующую возможность \texttt{push-options} в список передаваемых сервером ссылок при первом к нему запросе --- в противном случае опции игнорируются. После обновления ссылок push"=опции становятся доступны post"=receive хуку через переменные окружения: количество опций передаётся в \texttt{GIT\_PUSH\_OPTION\_COUNT}, а сами значения --- в \texttt{GIT\_PUSH\_OPTION\_0}, \texttt{GIT\_PUSH\_OPTION\_1} и так далее \cite{githooks}.

\section{Реализация подсистемы отправки студенческих решений}

Было спроектировано и реализовано серверное приложение на языке Go. Оно предоставляет две точки входа: HTTP API для работы через веб"=интерфейс и SSH"=сервер для взаимодействия через Git.

Приложение состоит из нескольких уровней абстракции. Каждый уровень отвечает за строго определённую задачу и взаимодействует только с соседними через интерфейсы:

\begin{itemize}
	\item слой обработки входящих запросов, который разбирает HTTP или SSH"=запросы, вызывает сервис, формирует ответ, не содержит бизнес"=логики;
	\item сервисный слой, а то есть бизнес"=логика приложения: валидация, оркестрация операций, вызов хранилища;
	\item слой доступа к данным для работы с хранилищем, определён в каждом домене независимо.
\end{itemize}

Реализацией интерфейсов доступа к данным служит единый модуль, работающий через PostgreSQL (с помощью библиотеки \texttt{sqlx}). Связывание уровней выполняется в функции \texttt{main} --- каждая зависимость явно создаётся и передаётся конструктору следующего уровня. Это упрощает тестирование: каждый сервис можно проверить с подставной реализацией репозитория.

HTTP API реализован на фреймворке Huma v2, который автоматически генерирует OpenAPI"=спецификацию по аннотациям Go"=структур.

SSH"=сервер построен на библиотеке Charm Wish и работает на отдельном порту (2222 по умолчанию). Запуск сервера осуществляется через функцию библиотеки Charm Wish в функции main:

\begin{minted}[linenos, breaklines=true, style=bw, fontsize=\small]{go}
sshServer, err := wish.NewServer(
    wish.WithAddress(
        net.JoinHostPort(config.Host, strconv.Itoa(config.SSHPort)),
    ),
    wish.WithHostKeyPath(".ssh/id_ed25519"),
    ssh.PublicKeyAuth(gitService.CheckPublicKeyAuth),
    ssh.PasswordAuth(gitService.CheckPasswordAuth),
    wish.WithMiddleware(
        pkggit.Middleware("repos", gitService.RepoRename, gitService),
        gitService.GitListMiddleware,
        logging.Middleware(),
    ),
)
\end{minted}

Промежуточный слой (middleware) \texttt{pkggit.Middleware} перехватывает каждую SSH"=сессию и анализирует её команду. Команда должна содержать ровно два аргумента: имя Git"=команды (\texttt{git-upload-pack}, \texttt{git-receive-pack} или \texttt{git-upload-archive}) и путь к репозиторию в формате \texttt{<имя курса>/<имя группы задач>}.

В \texttt{pkggit.Middleware} выполняется пользовательская логика (аутентификация по ключу, связь с репозиторием пользователя), а потом в зависимости от команды запускается \texttt{GitPack}, который через функцию \texttt{RunGit} делегирует работу нативному бинарному Git, пробрасывая его потоки ввода и вывода напрямую в SSH"=сессию.

После успешного завершения вызываются функции \texttt{OnPush} или \texttt{OnFetch}. Если команда не является Git"=командой, управление передаётся следующему middleware в цепочке (например, \texttt{GitListMiddleware}, показывающему меню репозиториев).

Такой подход позволяет использовать стандартный Git"=клиент без модификаций --- студенту достаточно добавить SSH"=ключ в аккаунт на платформе и клонировать репозиторий, а остальная логика для связи Git с образовательной платформой реализуется как раз с помощью \texttt{pkggit.Middleware}. Полный код представлен в приложении~\ref{sec:Middleware}.

\subsection{Реализация Git"=сервера и аутентификация}

Для приёма решений через Git необходимо обеспечить два ключевых механизма: аутентификацию пользователей и привязку Git"=репозитория к конкретному курсу, заданию и студенту.

\subsubsection{Аутентификация по SSH"=ключам}

Пользователь может добавить один или несколько публичных SSH"=ключей в свой аккаунт через HTTP API (маршруты \path{POST /git/add_key} и \path{DELETE /git/delete_key}). Ключи хранятся в таблице \texttt{ssh\_keys} базы данных, связываясь с пользователем через ключ на таблицу \texttt{users}. При подключении по SSH сервер Charm Wish, вызывает обработчик \texttt{PublicKeyAuth}, который ищет отпечаток предложенного ключа в базе:

\begin{minted}[linenos, breaklines=true, style=bw, fontsize=\small]{go}
func (r *PGRepo) CheckPublicKeyAuth(ctx ssh.Context, pk ssh.PublicKey) bool {
    fingerprint := gossh.FingerprintSHA256(pk)
    _, err := r.GetParticipant(fingerprint)
    return err == nil
}
\end{minted}

Если ключ найден, аутентификация считается успешной, и идентификатор пользователя становится известен на весь остаток сессии.

Такой подход отличается от стандартного OpenSSH"=демона: ключи управляются через базу данных, а не через файл \texttt{authorized\_keys}. Это позволяет добавлять и отзывать ключи через веб"=интерфейс без доступа к серверу и без перезагрузки SSH"=демона.

\subsubsection{Маршрутизация репозиториев}

Когда пользователь выполняет \path{git} \path{push} \path{ssh://host:2222/course_name/task_name}, промежуточный обработчик \texttt{RepoRename} преобразует путь \path{course_name/task_name} в детерминированное имя репозитория. Алгоритм преобразования:

\begin{enumerate}
	\item По имени курса из базы находится \texttt{CourseID} (идентификатор курса).
	\item По имени группы заданий \texttt{TaskGroupID} (идентификатор группы заданий).
	\item По отпечатку SSH"=ключа  \texttt{UserID} (идентификатор студента).
	\item Из трёх идентификаторов формируется строка вида \path{CourseID:TaskGroupID:UserID}, от которой вычисляется SHA"=1 хеш:

	      \begin{minted}[linenos, breaklines=true, style=bw, fontsize=\small]{go}
func (repoID *RepoID) IntoPath() string {
    hasher := sha1.New()
    data, _ := json.Marshal(repoID)
    hasher.Write(data)
    hashSum := hasher.Sum(nil)
    return hex.EncodeToString(hashSum)
}
\end{minted}

	\item Итоговый путь репозитория --- \texttt{repos/<hash>.git}.
\end{enumerate}

Детерминированность пути гарантирует, что все операции одного студента над одной группой заданий попадают в один и тот же репозиторий.

Полный код функции \path{RepoRename} представлен в приложении~\ref{sec:RepoRename}.

\subsubsection{Разграничение доступа}

После аутентификации промежуточный слой проверяет уровень доступа к репозиторию через функцию \texttt{AuthRepo}:

\begin{minted}[linenos, breaklines=true, style=bw, fontsize=\small]{go}
func (s *Service) AuthRepo(repo string, pk ssh.PublicKey) pkggit.AccessLevel {
    if s.db.CheckPublicKeyAuth(nil, pk) {
        return pkggit.ReadWriteAccess
    }
    return pkggit.NoAccess
}
\end{minted}

Возможные уровни доступа:

\begin{itemize}
	\item \texttt{NoAccess} --- пользователь не является участником курса или не имеет прав, операция отклоняется;
	\item \texttt{ReadOnlyAccess} --- пользователь может клонировать репозиторий и получать обновления;
	\item \path{ReadWriteAccess} --- пользователь может отправлять изменения;
	\item \texttt{AdminAccess} --- полный доступ, включая управление шаблонами и правами.
\end{itemize}

Уровень доступа определяется по таблице \texttt{course\_members}: студент получает ReadWriteAccess к своему репозиторию, преподаватель --- AdminAccess ко всем репозиториям курса.

\subsection{Отправка решений}

\subsubsection{Процесс отправки с помощью \texttt{git push}}

Процесс отправки решений на образовательной платформе с использованием Git реализован с помощью его же функциональности, описанной в разделе~\ref{sec:gitwire}.

Студент сначала должен создать тег, а потом отправить его с указанием номера задания в push"=options:

\begin{minted}[frame=none,fontsize=\small]{text}
git tag submission-1
git push origin submission-1 -o "1"
\end{minted}

Промежуточный слой SSH перехватывает команду \texttt{git-receive-pack} и запускает нативный бинарный Git. В bare"=репозиторий предварительно записаны два сценария Git (hooks):

\begin{enumerate}
	\item pre"=receive --- выполняется после получения файлов от клинта, до обновления ссылок. Его исходный код (см. приложение \ref{sec:script1}) автоматически записывается в каждый bare"=репозиторий при его инициализации. Скрипт читает push"=опции из переменной окружения \texttt{GIT\_PUSH\_OPTION\_0}, извлекает номер задания, находит соответствующие паттерны в файле \texttt{.patterns} и через \texttt{git ls-tree} проверяет каждый файл коммита. Если ни один файл не совпал --- хук возвращает ошибку, и операция отклоняется;

	\item post"=receive --- выполняется после обновления ссылок. Скрипт (см. приложение \ref{sec:script2}) записывает хеши принятых тегов в файл \texttt{push-tags}, а push"=опции --- в \texttt{push-options}.
\end{enumerate}

После завершения работы хуков на стороне Git сервера вызывается функция \texttt{OnPush}. Она выполняет следующие действия: извлекает идентификатор студента по отпечатку SSH"=ключа через \texttt{GetRepoID}, читает файл \texttt{push-options} (записанный post"=receive хуком) и извлекает номер задания из push"=опций. Если номер больше единицы --- проверяет через \texttt{HasSubmittedAttempt}, что предыдущее задание уже сдано (последовательная сдача обязательна). Затем находит \texttt{TaskID} по номеру позиции в группе заданий, читает файл \texttt{push-tags} с хешами принятых тегов и для каждого хеша сохраняет попытку в базу данных через \texttt{SaveAttempt}. Файлы \texttt{push-options} и \texttt{push-tags} после чтения удаляются. Код представлен в приложении~\ref{sec:OnPush}.

\subsubsection{Альтернативный сценарий: push через веб"=интерфейс}

Система также поддерживает отправку решений через веб"=интерфейс. Пользователь загружает ZIP"=архив с файлами решения через маршрут \texttt{POST /attempts}. Сервер:

\begin{enumerate}
	\item Распаковывает архив во временную директорию.
	\item Если bare"=репозиторий студента ещё не существует, инициализирует его из шаблона (если шаблон предусмотрен) или создаёт пустой.
	\item Клонирует bare"=репозиторий во временную рабочую директорию.
	\item Записывает файлы, создаёт коммит от имени системного пользователя \texttt{mm-backend}.
	\item Выполняет push обратно в bare"=репозиторий.
	\item Регистрирует попытку с хешем созданного коммита.
\end{enumerate}

Оба сценария записывают данные в один и тот же репозиторий и проходят одинаковую валидацию последовательности, что позволяет пользователю работать и через веб"=страницу, и через CLI, и совмещая оба эти варианта.

Код функций, реализующих это представлен в приложении~\ref{sec:webpush}.

\subsection{Комбинированная модель хранения}

Для хранения попыток используется комбинированная модель: Git отвечает за версионирование файлов, а реляционная база данных PostgreSQL --- за метаданные и состояние попыток.

\subsubsection{Хранение файлов в Git}

Каждый bare"=репозиторий на диске содержит полную историю изменений файлов студента. Git, как было показано в разделе~\ref{sec:comparison}, предоставляет контентно"=адресуемое хранилище: одинаковые файлы не дублируются, каждый коммит является полным слепком файлового дерева, а целостность данных проверяется через SHA"=1 хеши. Репозиторий студента содержит все его попытки по всем заданиям данной группы --- каждая попытка представлена отдельным тегом, указывающим на соответствующий коммит.

\subsubsection{Хранение метаданных в PostgreSQL}

Метаданные попыток хранятся в двух связанных таблицах:

\begin{itemize}
	\item \texttt{attempts} --- связывает пользователя с заданием, содержит их идентификаторы;
	\item \texttt{attempt\_transitions} --- хранит историю состояний попытки: предыдущее и новое состояние (например, \texttt{submitted} $\to$ \texttt{graded}), временную метку и JSON"=объект с дополнительными данными, включая хеш коммита.
\end{itemize}

Механизм гарантирует, что повторная отправка не перезаписывает предыдущую попытку, а создаёт новый переход. Хеш коммита, сохранённый в поле \path{transition_data} таблицы, скрипт создания которой представлен ниже, связывает метаданные в PostgreSQL с содержимым в Git.

\begin{minted}[linenos, breaklines=true, style=bw, fontsize=\small]{sql}
CREATE TABLE attempts (
    id uuid NOT NULL PRIMARY KEY DEFAULT uuidv7(),
    user_id uuid NOT NULL REFERENCES users(id),
    task_id uuid NOT NULL REFERENCES tasks(id)
);
CREATE TABLE attempt_transitions (
    attempt_id uuid NOT NULL REFERENCES attempts(id),
    state attempt_state NOT NULL,
    transition_at timestamp NOT NULL,
    transition_data jsonb
);
\end{minted}

\subsubsection{Шаблоны решений}

Преподаватель может загрузить шаблон решения через маршрут \texttt{POST /tasks/\{id\}/template} в виде ZIP"=архива. Сервер распаковывает архив и вызывает функцию \texttt{UpdateTemplate} (приложение~\ref{sec:template}), которая создаёт или обновляет bare"=репозиторий шаблона. Имя репозитория вычисляется детерминированно через SHA"=1 от идентификатора группы заданий:

\begin{minted}[linenos, breaklines=true, style=bw, fontsize=\small]{go}
func TemplatePath(taskGroupID uuid.UUID) string {
	hasher := sha1.New()
	_, _ = fmt.Fprint(hasher, "template:", taskGroupID.String())
	hashSum := hasher.Sum(nil)
	return hex.EncodeToString(hashSum)
}
\end{minted}

При первой отправке решения студентом система вызывает функцию \path{initRepoWithTemplate}. Если шаблон существует, функция клонирует его во временную директорию, инициализирует пустой bare"=репозиторий студента и выполняет push из временной копии в репозиторий студента. Если шаблон не предусмотрен, репозиторий инициализируется пустым. Код функции \path{initRepoWithTemplate} представлен в приложении \ref{sec:initRepoWithTemplate}.

\subsubsection{Сравнение версий}

\texttt{GET /attempts/diff} позволяет получить разницу между двумя попытками. Параметрами запроса передаются идентификаторы попыток. Сервер открывает bare"=репозиторий, извлекает хеши коммитов из соответствующих записей \texttt{attempt\_transitions} и выполняет \texttt{git diff} между ними:

\begin{minted}[linenos, breaklines=true, style=bw, fontsize=\small]{go}
func (s *Service) GetDiff(attemptID1, attemptID2 uuid.UUID) ([]string, error) {
    info1, _ := s.db.GetAttemptCommitInfo(attemptID1)
    info2, _ := s.db.GetAttemptCommitInfo(attemptID2)
    repoID := RepoID{
        CourseID:      info1.CourseID,
        TaskGroupID:   info1.TaskGroupID,
        ParticipantID: info1.UserID,
    }
    repo, _ := gogit.PlainOpen(
        filepath.Join(repoDir, repoID.IntoPath()+".git"),
    )
    commit1, _ := repo.CommitObject(plumbing.NewHash(info1.CommitHash))
    commit2, _ := repo.CommitObject(plumbing.NewHash(info2.CommitHash))
    patch, _ := commit1.Patch(commit2)
    patterns, _ := s.db.GetTaskPatternsByTaskID(
        context.Background(), info1.TaskID,
    )
    if len(patterns) > 0 {
        return filterDiffByPatterns(patch, patterns), nil
    }
    return strings.Split(patch.String(), "\n"), nil
}
\end{minted}

Если задание определяет паттерны файлов (glob"=маски), diff фильтруется --- показываются только изменения в файлах, соответствующих заданию. Это позволяет преподавателю видеть только релевантные изменения, игнорируя служебные файлы.

\begin{minted}[linenos, breaklines=true, style=bw, fontsize=\small]{go}
func Middleware(
	repoDir string,
	RepoRename func(string, gossh.PublicKey) (string, error),
	gh Hooks,
) wish.Middleware {
	return func(sh ssh.Handler) ssh.Handler {
		return func(s ssh.Session) {
			cmd := s.Command()
			if len(cmd) == 2 {
				gc := cmd[0]
				pk := s.PublicKey()
				rawRepo := cmd[1]
				repo, err := RepoRename(rawRepo, pk)
				if err != nil {
					log.Error("repo rename failed", "error", err, "repo", rawRepo)
					Fatal(s, err)
					return
				}
				access := gh.AuthRepo(repo, pk)
				switch GitCmd(gc) {
				case GitReceivePack:
					switch access {
					case ReadWriteAccess, AdminAccess:
						if err := GitPack(s, gc, repoDir, repo); err != nil {
							log.Error("git push failed", "error", err, "repo", rawRepo)
							Fatal(s, ErrSystemMalfunction)
						} else {
							gh.OnPush(rawRepo, repo, pk)
						}
					default:
						Fatal(s, ErrNotAuthed)
					}
					return
				case GitUploadPack, GitUploadArchive:
					switch access {
					case ReadOnlyAccess, ReadWriteAccess, AdminAccess:
						if err := GitPack(s, gc, repoDir, repo); err != nil {
							switch {
							case errors.Is(err, ErrInvalidRepo):
								Fatal(s, ErrInvalidRepo)
							default:
							log.Error("unknown git error", "error", err)
							Fatal(s, ErrSystemMalfunction)
							}
						} else {
							gh.OnFetch(rawRepo, repo, pk)
						}
					default:
						Fatal(s, ErrNotAuthed)
					}
					return
				}
			}
			sh(s)
		}
	}
}
\end{minted}

\section{Программный код скрипта \texttt{pre-recieve}}
\label{sec:script1}

\begin{minted}[linenos, breaklines=true, style=bw, fontsize=\small]{bash}
    #!/bin/sh
PATTERNS_FILE="$GIT_DIR/.patterns"

TASK_POS=""
if [ -n "$GIT_PUSH_OPTION_COUNT" ] && [ "$GIT_PUSH_OPTION_COUNT" -gt 0 ]; then
    i=0
    while [ $i -lt "$GIT_PUSH_OPTION_COUNT" ]; do
        eval "opt=\$GIT_PUSH_OPTION_$i"
        case "$opt" in
            ''|*[!0-9]*) ;;
            *) TASK_POS="$opt" ;;
        esac
        i=$((i+1))
    done
fi

while read OLD NEW REF; do
    case "$REF" in
        refs/heads/*) continue ;;
        refs/tags/*)
            [ "$OLD" != "0000000000000000000000000000000000000000" ] && echo "ERROR: tag updates not allowed" >&2 && exit 1
            ;;
        *) continue ;;
    esac
    [ -z "$TASK_POS" ] && continue
    [ -f "$PATTERNS_FILE" ] || continue
    PATTERNS=$(grep "^$TASK_POS:" "$PATTERNS_FILE" | cut -d: -f2-)
    [ -z "$PATTERNS" ] && continue
    FILES=$(git ls-tree --name-only -r "$NEW" 2>/dev/null)
    [ -z "$FILES" ] && continue
    for file in $FILES; do
        for pattern in $PATTERNS; do
            case "$file" in
                $pattern) exit 0 ;;
            esac
        done
    done
    echo "ERROR: no files match required patterns for task $TASK_POS ($PATTERNS)" >&2
    exit 1
done

func (s *Service) OnPush(originalPath string, repo string, pk ssh.PublicKey) {
    fingerprint := gossh.FingerprintSHA256(pk)
    repoID, err := s.GetRepoID(originalPath, fingerprint)
    if err != nil {
        return
    }

    shaPath := repoID.IntoPath() + ".git"
    repoBase := filepath.Join(repoDir, shaPath)

    optionsData, err := os.ReadFile(filepath.Join(repoBase, "push-options"))
    if err != nil {
        return
    }
    defer os.Remove(filepath.Join(repoBase, "push-options"))

    pos := parseNumericPosition(
        strings.Split(strings.TrimSpace(string(optionsData)), "\n"),
    )
    if pos == 0 {
        return
    }

    if pos > 1 {
        ok, err := s.db.HasSubmittedAttempt(
            context.Background(),
            repoID.ParticipantID, repoID.TaskGroupID, pos-1,
        )
        if err != nil || !ok {
            return
        }
    }

    taskID, err := s.db.GetTaskIDByPosition(
        context.Background(), repoID.TaskGroupID, pos,
    )
    if err != nil {
        return
    }

    tagsData, err := os.ReadFile(filepath.Join(repoBase, "push-tags"))
    if err != nil {
        return
    }
    defer os.Remove(filepath.Join(repoBase, "push-tags"))

    for _, hashStr := range strings.Fields(string(tagsData)) {
        s.db.SaveAttempt(repoID, taskID, hashStr)
    }
}

func (s *Service) PushAttempt(repoID RepoID, taskID uuid.UUID, files []FileInfo) (string, error) {
	repoName := repoID.IntoPath()
	bareRepoPath := filepath.Join(repoDir, repoName+".git")

	if _, err := os.Stat(bareRepoPath); os.IsNotExist(err) {
		if err := s.initRepoWithTemplate(repoID); err != nil {
			return "", fmt.Errorf("init repo: %w", err)
		}
		patterns, err := s.db.GetTaskPatterns(context.Background(), repoID.TaskGroupID)
		if err != nil {
			zap.L().Warn("PushAttempt: get patterns", zap.Error(err))
		} else if len(patterns) > 0 {
			if err := WritePatternsFile(bareRepoPath, patterns); err != nil {
				zap.L().Warn("PushAttempt: write patterns file", zap.Error(err))
			}
		}
	}

	tmpDir, err := os.MkdirTemp("", "attempt-*")
	if err != nil {
		return "", fmt.Errorf("create temp dir: %w", err)
	}
	defer func() {
		if err := os.RemoveAll(tmpDir); err != nil {
			zap.L().Error("removing tmp dir", zap.Error(err))
		}
	}()

	repo, err := gogit.PlainClone(tmpDir, &gogit.CloneOptions{
		URL: bareRepoPath,
	})
	if err != nil {
		_ = os.RemoveAll(tmpDir)
		if err := os.MkdirAll(tmpDir, 0o700); err != nil {
			return "", fmt.Errorf("recreate tmp dir: %w", err)
		}

		repo, err = gogit.PlainInit(tmpDir, false)
		if err != nil {
			return "", fmt.Errorf("init work repo: %w", err)
		}

		if _, err := repo.CreateRemote(&config.RemoteConfig{
			Name: "origin",
			URLs: []string{bareRepoPath},
		}); err != nil {
			return "", fmt.Errorf("create remote: %w", err)
		}
	}

	wt, err := repo.Worktree()
	if err != nil {
		return "", fmt.Errorf("get worktree: %w", err)
	}

	for _, f := range files {
		path := filepath.Join(tmpDir, f.FileName)

		if err := os.MkdirAll(filepath.Dir(path), 0o700); err != nil {
			return "", fmt.Errorf("create dirs for %s: %w", f.FileName, err)
		}

		if err := os.WriteFile(path, f.Content, 0o644); err != nil {
			return "", fmt.Errorf("write %s: %w", f.FileName, err)
		}

		if _, err := wt.Add(f.FileName); err != nil {
			return "", fmt.Errorf("git add %s: %w", f.FileName, err)
		}
	}

	commitHash, err := wt.Commit("web attempt", &gogit.CommitOptions{
		Author: &object.Signature{
			Name:  "mm-backend",
			Email: "mm-backend@mergeminds",
			When:  time.Now(),
		},
	})
	if err != nil {
		return "", fmt.Errorf("commit: %w", err)
	}

	if err := repo.Push(&gogit.PushOptions{
		RemoteName: "origin",
	}); err != nil {
		return "", fmt.Errorf("push: %w", err)
	}

	if err := s.db.SaveAttempt(repoID, taskID, commitHash.String()); err != nil {
		return "", fmt.Errorf("save attempt: %w", err)
	}

	zap.L().Info(
		"attempt pushed",
		zap.String("repo", repoName),
		zap.String("commit", commitHash.String()),
	)

	return commitHash.String(), nil
}

func UnzipFiles(data []byte) ([]FileInfo, error) {
	reader, err := zip.NewReader(bytes.NewReader(data), int64(len(data)))
	if err != nil {
		return nil, err
	}

	var files []FileInfo
	for _, f := range reader.File {
		if f.FileInfo().IsDir() {
			continue
		}

		rc, err := f.Open()
		if err != nil {
			return nil, fmt.Errorf("open %s: %w", f.Name, err)
		}

		content, err := io.ReadAll(rc)
		if cerr := rc.Close(); cerr != nil {
			zap.L().Warn("close file reader", zap.String("file", f.Name), zap.Error(cerr))
		}
		if err != nil {
			return nil, fmt.Errorf("read %s: %w", f.Name, err)
		}

		files = append(files, FileInfo{
			FileName:   f.Name,
			FileSize:   int64(len(content)),
			UploadedAt: time.Now(),
			Content:    content,
		})
	}

	return files, nil
}
