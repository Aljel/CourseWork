\intro

Современное высшее образование, особенно в области информационных технологий, находится в условиях активной трансформации. Вызвано это как нехваткой квалифицированных кадров на рынке труда, так и ростом числа желающих развиваться в IT индустрии. На фоне развития отрасли традиционные образовательные подходы и методики обучения теряют свою актуальность, становятся недостаточно эффективными в подготовке специалистов. Стандартные системы не всегда способны обеспечить необходимую гибкость, интерактивность и практическую направленность, которые востребованы в условиях быстро меняющегося рынка.

Под влиянием данных факторов активно развиваются цифровые образовательные платформы --- LMS (системы управления обучением). Такие системы автоматизируют администрирование учебных курсов, управляют расписанием и успеваемостью, предоставляют инструменты для коммуникации и совместной работы. Системы также должны предоставлять удобные интерфейсы для сдачи и проверки заданий, которые студенты выполняют в рамках курсов.

В индустрии информационных технологий для решения проблем версионирования, эффективного хранения проектов и организации совместной работы над ними широко применяются системы контроля версий (VCS), в частности Git. Освоение навыков работы с Git является фундаментальным требованием для будущих специалистов, поскольку этот инструмент является стандартом в современной разработке программного обеспечения. Интеграция Git в образовательный процесс, позволяющая студентам повседневно использовать его для сдачи и управления своими заданиями, способствует формированию профессиональных компетенций и облегчает их последующую адаптацию к требованиям рынка труда.

Целью данной работы является проектирование и реализация части образовательной платформы --- узкоспециализированной LMS для IT-специальностей, --- которая использует Git для версионирования студенческих заданий, эффективного хранения данных, а также обладает функционалом для удобной сдачи и проверки решений.

В ходе работы должны быть решены следующие задачи:
\begin{itemize}
	\item проанализировать существующие подходы к хранению программного кода, выявив преимущества систем контроля версий на базе Git;
	\item исследовать современные стандарты обмена данными между клиентом и сервером в контексте образовательной платформы;
	\item изучить роль протокола SSH в передаче данных через инструмент Git;
	\item спроектировать процесс взаимодействия студентов с подсистемой хранения решений через CLI-интерфейс и веб-версию платформы;
	\item создать комбинированную модель хранения попыток, совмещающую Git для файлов и реляционную базу данных для метаданных.
\end{itemize}

\section{Архитектурный стиль REST для построения основного сервера образовательной платформы}

REST (Representational State Transfer) --- это архитектурный стиль для построения распределённых гипермедиа-систем, предложенный Роем Филдингом в 2000 году \cite{fielding2000architectural}. REST определяет набор ограничений, которые при совместном применении обеспечивают масштабируемость, производительность и простоту поддержки веб-сервисов.

REST оперирует концепцией ресурсов. Ресурс --- это любой объект, доступ к которому осуществляется через уникальный идентификатор (URL). Взаимодействие с ресурсами выполняется с помощью стандартных HTTP-методов: GET для получения, POST для создания, PUT для полного обновления, PATCH для частичного обновления, DELETE для удаления \cite{fielding2000architectural}.

Основные ограничения REST:

\begin{itemize}
	\item клиент-сервер --- клиент и сервер разделены и общаются только через запросы и ответы, что позволяет развивать их независимо;
	\item отсутствие состояния --- каждый запрос содержит всю информацию, необходимую для его обработки, сервер не хранит контекст между запросами, что упрощает масштабирование и повышает отказоустойчивость \cite{fielding2000architectural};
	\item кеширование --- ответы сервера могут быть явно помечены как кешируемые, клиенты и промежуточные узлы могут повторно использовать закешированные ответы, снижая нагрузку на сервер \cite{richardson2013restful};
	\item единообразие интерфейса --- все ресурсы идентифицируются через URL, а операции над ними выполняются стандартными HTTP-методами, что делает API предсказуемым и упрощает интеграцию;
	\item многоуровневая система --- между клиентом и сервером могут находиться промежуточные узлы (балансировщики, прокси), каждый уровень видит только соседний \cite{richardson2013restful}.
\end{itemize}

REST не является единственным подходом к построению веб-сервисов. В качестве альтернатив можно выделить SOAP --- протокол со строгой типизацией и формальными XML-схемами, требующий дополнительных инструментов для реализации и потому более громоздкий в настройке по сравнению с REST. RPC-стиль сводит взаимодействие к вызову удалённых функций, однако не стандартизирует работу с ресурсами, что затрудняет построение предсказуемого API. GraphQL предоставляет клиенту гибкость в выборе возвращаемых полей за счёт более сложной схемы на стороне сервера. Выбор REST в качестве архитектурного стиля для данной работы обусловлен его простотой, единообразием интерфейса и использованием стандартных возможностей HTTP без дополнительных протоколов \cite{richardson2013restful}.

\section{Сравнительный анализ подходов к хранению программного кода}
\label{sec:comparison}

Чтобы оценить, насколько тот или иной подход годится для хранения версионированного кода, нужна система координат. В теории баз данных для этого есть ACID --- набор свойств, которым должна удовлетворять надёжная система \cite{haerder1983principles}. Сам термин ввели Тео Хардер и Андреас Ройтер в 1983 году \cite{haerder1983principles}, опираясь на работы Джима Грея по транзакциям \cite{gray1981transaction}. Расшифровывается так:

\begin{itemize}
	\item Atomicity (атомарность) --- операция выполняется целиком или не выполняется вовсе;
	\item Consistency (согласованность) --- система всегда остаётся в корректном состоянии; инварианты не нарушаются;
	\item Isolation (изоляция) --- параллельные операции не влияют друг на друга;
	\item Durability (долговечность) --- если данные сохранены, они переживают сбой.
\end{itemize}

Разберём три подхода к хранению кода, ориентируясь на ACID.

\subsection{Хранение файлов в реляционных СУБД (BLOB-объекты)}

BLOB (Binary Large Object) --- тип данных в реляционных СУБД для хранения бинарных данных \cite{garcia2009database}. Если хранить код в BLOB, каждая попытка --- строка в таблице с полем типа BLOB.

Проблема в том, что реляционная модель не рассчитана на версионирование древовидных структур. BLOB --- чёрный ящик для базы данных: она не знает, что внутри, и не может гарантировать согласованность содержимого. Consistency из ACID работает на уровне строки, но не на уровне структуры проекта \cite{postgresacid}.

Также, если задание состоит из нескольких файлов, нет атомарного обновления набора файлов как единого целого без дополнительной обвязки. Isolation могла бы давать изоляцию строк, но при конкурентной записи в BLOB возможны проблемы, описанные в документации PostgreSQL \cite{postgresacid}. Сравнение версий требует выгрузки BLOB-ов наружу, для чего не располагает база данных.

BLOB решает задачу «просто сохранить байты», но не решает задачу «хранить версионированный код с историей». ACID-гарантии, которые СУБД даёт для чисел и строк, почти не работают для этого сценария.

\subsection{Хранение файлов на файловой системе}

Второй подход --- хранить каждую версию как набор файлов в директории на диске. Файловая система предоставляет базовые операции чтения и записи, но не является системой управления данными: в ней нет встроенных механизмов версионирования, атомарных групповых операций или средств контроля целостности. Каждая операция записи работает с отдельным файлом, и если в процессе записи нескольких файлов произойдёт сбой, часть данных может быть потеряна, а согласованность директории --- нарушена.

Кроме того, файловая система не хранит историю изменений: после перезаписи файла предыдущее состояние становится недоступным. Для реализации версионирования поверх файловой системы потребуется дополнительный слой, который будет отслеживать изменения и управлять копиями --- по сути, реализовывать функциональность, уже встроенную в Git.

\subsection{Преимущества систем контроля версий на базе Git}

Git --- это распределенная система контроля версий, созданная Линусом Торвальдсом в 2005 году для разработки ядра Linux. Сегодня это стандартный инструмент для управления исходным кодом практически в любом IT-проекте \cite{chacon2014pro}.

В отличие от многих других систем, Git не хранит списки изменений между версиями. Вместо этого Git хранит полные слепки (snapshots) файлового дерева на каждый момент коммита. Такая схема хранения оказывается эффективнее за счет переиспользования неизмененных объектов.

В основе Git лежит \quot{контентно-адресуемое хранилище} (content-addressable storage). Фактически Git --- это база данных «ключ --- значение», где ключом является SHA-1 хеш содержимого, а значением --- сами данные \cite{chacon2014pro}\cite{aosagit}. Git использует четыре типа объектов:

\begin{itemize}
	\item Blob --- содержимое файла. У blob-объекта нет имени файла, это просто набор байт. Если два разных файла имеют одинаковое содержимое, они будут ссылаться на один и тот же blob --- это позволяет избегать дублирования информации;
	\item Tree --- аналог директории. Содержит список записей вида \quot{имя файла --- ссылка на blob} или \quot{имя поддиректории --- ссылка на другой tree};
	\item Commit --- ссылается на корневой tree (полный слепок репозитория), на ноль или более родительских коммитов, а также хранит метаданные: автор, дата, сообщение;
	\item Tag --- именованная ссылка на коммит, обычно для обозначения версий.
\end{itemize}

Git позволяет экономить место на диске. При создании нового \quot{коммита}, Git не копирует все файлы заново. Вместо этого он создает новые blob-объекты только для измененных файлов. Файлы, которые не менялись, продолжают ссылаться на уже существующие объекты \cite{gitchaconobjects}. Например, если в проекте из 100 файлов изменился один, Git создаст один новый blob, новый tree (для директории с измененным файлом) и новый commit. Остальные 99 файлов останутся на своих старых blob-объектах. Получается, что каждый коммит --- это полноценный снимок всего репозитория, но занимает он места ровно столько, сколько нужно для описания изменений.

Каждый объект в Git идентифицируется SHA-1 хешем содержимого. Если байт в объекте изменится, хеш перестанет соответствовать, и Git обнаружит повреждение \cite{chacon2014pro}.

Коммиты в Git образуют направленный ациклический граф (DAG) \cite{aosagit}. Каждый коммит ссылается на родительские коммиты, что позволяет восстановить полную историю изменений. Ветвление --- создание нового указателя на коммит. Ветки в Git --- легковесные ссылки, которые создаются и удаляются за миллисекунды.

Перечисленные свойства делают Git подходящей основой для подсистемы приёма студенческих решений. История коммитов даёт преподавателю возможность проследить эволюцию решения от первой до последней попытки. Поскольку каждый коммит --- полный слепок файлового дерева, diff между любыми двумя попытками вычисляется средствами Git без дополнительных усилий. Контентно-адресуемое хранение устраняет дублирование файлов, одинаковых между попытками --- повторно отправленные без изменений файлы не занимают места. Теги позволяют пометить конкретные коммиты как сданные попытки. Наконец, Git является стандартом в индустрии, и его использование в учебном процессе формирует у студентов профессиональные навыки, востребованные на рынке труда.

\section{Принципы работы протокола SSH}

SSH (Secure Shell) --- протокол безопасного удаленного доступа к серверам. Разработан в 1995 году финской компанией SSH Communications Security как замена небезопасным протоколам Telnet и rsh, которые передавали данные (включая пароли) в открытом виде \cite{rfc4251}.

Основная проблема, которую решает SSH: как двум компьютерам общаться по незащищенному каналу (Интернету) так, чтобы никто не мог перехватить, прочитать или подменить передаваемые данные?

Архитектура SSH (RFC 4251) состоит из трех уровней и первый из них --- транспортный протокол (RFC 4253). Этот уровень работает поверх TCP и отвечает за установление защищенного соединения. Сначала сервер предъявляет свой host-ключ --- клиент проверяет, что он подключился именно к тому серверу, к которому собирался. Затем стороны выполняют обмен ключами по протоколу Диффи-Хеллмана, в результате которого получают общий секретный ключ. После этого весь трафик шифруется симметричным шифром (например, AES). Важная особенность --- \quot{perfect forward secrecy}: даже если злоумышленник когда-нибудь узнает долговременный секретный ключ сервера, он не сможет расшифровать ранее перехваченные сессии \cite{rfc4253}.

После установки защищенного канала сервер проверяет подлинность клиента. Основные методы:
\begin{itemize}
	\item пароль --- классический способ, но пароль передаётся внутри защищённого канала;
	\item публичный ключ --- клиент доказывает, что владеет приватным ключом, соответствующим публичному ключу, который известен серверу;
	\item keyboard-interactive --- сервер задаёт клиенту вопросы (например, одноразовый пароль из SMS).
\end{itemize}

Аутентификация по публичному ключу --- способ, удобный для автоматизированных сценариев. Пользователь генерирует пару ключей: приватный (хранится только у владельца) и публичный (можно свободно распространять). Публичный ключ добавляется на сервер. При подключении SSH использует криптографию с открытым ключом: сервер отправляет случайное число и просит подписать его приватным ключом. Если подпись верна --- клиент доказал, что владеет приватным ключом, и аутентификация проходит успешно.

После аутентификации протокол соединения мультиплексирует несколько логических каналов внутри одного SSH-соединения. Через одно соединение можно одновременно передавать файлы, запускать несколько команд, пересылать порты.

Для использования SSH с Git не требуется стандартный OpenSSH-демон. Можно реализовать собственный SSH-сервер, который будет принимать подключения, проверять аутентификацию по ключам и выполнять нужные команды. Это дает возможность интегрировать аутентификацию с произвольным хранилищем данных --- например, проверять ключи через базу данных, а не через системные файлы authorized\_keys. Такой подход упрощает управление ключами и позволяет реализовать механизмы добавления и удаления ключей через API.

\section{Протокол Git Wire и его функционирование поверх SSH}

Когда разработчик выполняет \texttt{git push} или \texttt{git pull}, Git-клиент и Git-сервер обмениваются данными по определенному протоколу --- Git Wire Protocol \cite{gitprotocolpack}. Этот протокол определяет, как клиент и сервер договариваются о том, какие данные нужно передать, и как эти данные упаковываются в pack-файлы.

В Git существует два основных сценария передачи данных.

Клиент хочет получить данные с сервера. На сервере запускается процесс \texttt{git-upload-pack}, на клиенте --- \texttt{git-fetch-pack}. Последовательность шагов:
\begin{enumerate}
	\item Клиент подключается к серверу и запрашивает \texttt{git-upload-pack}.
	\item Сервер отправляет список ссылок (refs): какие ветки существуют и на какие коммиты они указывают.
	\item Клиент сообщает серверу, какие коммиты у него уже есть.
	\item Сервер вычисляет, каких объектов не хватает клиенту, упаковывает их в pack-файл и отправляет.
\end{enumerate}

Клиент хочет отправить данные на сервер. На сервере запускается \texttt{git-receive-pack}, на клиенте --- \texttt{git-send-pack}:
\begin{enumerate}
	\item Клиент подключается к серверу и запрашивает \texttt{git-receive-pack}.
	\item Сервер отправляет текущие ссылки.
	\item Клиент сообщает, какие ссылки он хочет обновить и какие новые объекты (коммиты, blob-ы) для этого нужны.
	\item Сервер проверяет, можно ли выполнить обновление (fast-forward?).
	\item Клиент упаковывает новые объекты в pack-файл и отправляет.
	\item Сервер принимает данные и обновляет ссылки.
	\item После успешного приема данных выполняются post-receive хуки.
\end{enumerate}

SSH-транспорт --- самый простой с точки зрения реализации: клиент запускает на сервере нужную команду через SSH и общается с ней через stdin/stdout \cite{gitprotocolpack}. Фактически, выполнение \texttt{git push ssh://server/repo} эквивалентно выполнению на сервере команды:

\texttt{ssh server "git-receive-pack '/repo.git'"}

После запуска процесса Git-клиент и Git-сервер общаются напрямую через stdin/stdout, а SSH обеспечивает шифрование и аутентификацию.

Важная возможность Git-протокола --- push-опции (push options). Git позволяет передавать дополнительные параметры при push через флаг \texttt{-o} или \texttt{--push-option} \cite{gitprotocolpack}. Когда клиент отправляет push-опции, они передаются серверному процессу и могут быть обработаны post-receive хуком \cite{githooks}.

Post-receive хук --- это скрипт, который выполняется после успешного приема данных. Он запускается в контексте Git-репозитория и может читать push-опции из переменных окружения. Хуки --- стандартный механизм Git, позволяющий добавлять произвольную логику на стороне сервера без модификации самого Git \cite{githooks}.

Сравнение SSH и HTTPS в контексте Git показывает, что у каждого транспорта есть свои особенности. HTTPS требует настройки веб-сервера и дополнительной аутентификации (базовый HTTP Auth). SSH предоставляет аутентификацию и шифрование \quot{из коробки}: достаточно добавить публичный ключ на сервер. SSH-сервер может работать независимо от основного HTTP-сервера, что упрощает разделение трафика \cite{chacon2014pro}.

\section{Архитектура серверного приложения}

На основе анализа, проведённого в предыдущих разделах, было спроектировано и реализовано серверное приложение на языке Go. Оно предоставляет две точки входа: HTTP API для работы через веб-интерфейс и SSH-сервер для взаимодействия через Git-клиент.

Приложение состоит из нескольких уровней абстракции. Каждый уровень отвечает за строго определённую задачу и взаимодействует только с соседними через интерфейсы:

\begin{itemize}
	\item слой обработки входящих запросов --- разбирает HTTP или SSH-запросы, вызывает сервис, формирует ответ. Не содержит бизнес-логики;
	\item сервисный слой --- бизнес-логика приложения: валидация, оркестрация операций, вызов хранилища;
	\item слой доступа к данным --- контракт на работу с хранилищем. Определён в каждом доменном пакете независимо.
\end{itemize}

Реализацией интерфейсов доступа к данным служит единый модуль, работающий через PostgreSQL (библиотека \texttt{sqlx}). Связывание уровней выполняется в функции \texttt{main} --- каждая зависимость явно создаётся и передаётся конструктору следующего уровня. Это упрощает тестирование: каждый сервис можно проверить с подставной реализацией репозитория.

HTTP API реализован на фреймворке Huma v2, который автоматически генерирует OpenAPI-спецификацию по аннотациям Go-структур.

SSH-сервер построен на библиотеке Charm Wish и работает на отдельном порту (2222 по умолчанию). Он принимает Git-команды (\texttt{git-upload-pack}, \texttt{git-receive-pack}), перенаправляет их к нативному бинарному Git, установленному в системе, и управляет доступом через базу данных. Такой подход позволяет использовать стандартный Git-клиент без модификаций --- студенту достаточно добавить SSH-ключ в аккаунт на платформе и клонировать репозиторий.

Хранилище данных состоит из трёх компонентов: PostgreSQL (пользователи, курсы, задания, попытки), Redis (Valkey) для сессий аутентификации и файловой системы для bare Git-репозиториев.

\section{Реализация Git-сервера и аутентификация}

Для приёма решений через Git необходимо обеспечить два ключевых механизма: аутентификацию пользователей и привязку Git-репозитория к конкретному курсу, заданию и студенту.

\subsection{Аутентификация по SSH-ключам}

Пользователь может добавить один или несколько публичных SSH-ключей в свой аккаунт через HTTP API (маршруты \path{POST /git/add_key} и \path{DELETE /git/delete_key}). Ключи хранятся в таблице \texttt{ssh\_keys} базы данных, связываясь с пользователем через ключ на таблицу \texttt{users}. При подключении по SSH сервер Charm Wish вызывает обработчик \texttt{PublicKeyAuth}, который ищет отпечаток предложенного ключа в базе. Если ключ найден, аутентификация считается успешной, и идентификатор пользователя становится известен на весь остаток сессии.

Такой подход отличается от стандартного OpenSSH-демона: ключи управляются через базу данных, а не через файл \texttt{authorized\_keys}. Это позволяет добавлять и отзывать ключи через веб-интерфейс без доступа к серверу и без перезагрузки SSH-демона.

\subsection{Маршрутизация репозиториев}

Когда пользователь выполняет \path{git} \path{push} \path{ssh://host:2222/course_name/task_name}, промежуточный обработчик \texttt{RepoRename} преобразует свободно заданный путь в детерминированное имя репозитория. Алгоритм преобразования:

\begin{enumerate}
	\item По имени курса из базы находится \texttt{CourseID}.
	\item По имени группы заданий --- \texttt{TaskGroupID}.
	\item По отпечатку SSH-ключа --- \texttt{UserID} (идентификатор студента).
	\item Из трёх идентификаторов формируется строка вида \path{CourseID:TaskGroupID:UserID}, от которой вычисляется SHA-1 хеш.
	\item Итоговый путь репозитория --- \texttt{repos/<hash>.git}.
\end{enumerate}

Детерминированность пути гарантирует, что все операции одного студента над одной группой заданий попадают в один и тот же репозиторий. При этом на одно задание может быть несколько попыток --- каждая оформляется как отдельный тег.

\subsection{Разграничение доступа}

После аутентификации промежуточный слой проверяет уровень доступа к репозиторию через функцию \texttt{AuthRepo}. Возможные уровни:

\begin{itemize}
	\item \texttt{NoAccess} --- пользователь не является участником курса или не имеет прав, операция отклоняется;
	\item \texttt{ReadOnlyAccess} --- пользователь может клонировать репозиторий и получать обновления;
	\item \path{ReadWriteAccess} --- пользователь может отправлять изменения;
	\item \texttt{AdminAccess} --- полный доступ, включая управление шаблонами и правами.
\end{itemize}

Уровень доступа определяется по таблице \texttt{course\_members}: студент получает ReadWriteAccess к своему репозиторию, преподаватель --- AdminAccess ко всем репозиториям курса.

\section{Приём решений через push-опции}

Git предоставляет возможность передавать произвольные строковые параметры вместе с операцией push (ключ \texttt{-o} или \texttt{--push-option}). На сервере эти параметры становятся доступны в переменных окружения сценариев Git. В разработанной системе push-параметры используются для указания номера задания, на которое сдаётся решение.

\subsection{Процесс push через SSH}

Студент создаёт тег и отправляет его с указанием номера задания:

\begin{minted}[frame=none,fontsize=\small]{text}
git tag submission-1
git push origin submission-1 -o "1"
\end{minted}

Промежуточный слой SSH перехватывает команду \texttt{git-receive-pack} и запускает нативный бинарный Git. В bare-репозиторий предварительно записаны два сценария Git (hooks):

\begin{enumerate}
	\item pre-receive --- выполняется до того, как сервер примет отправленные данные. Мы используем его, чтобы проверить, что тег ссылается на коммит, файлы которого соответствуют шаблону из файла \path{.patterns}. Этот файл генерируется автоматически при создании задания и содержит строки вида \path{<position>:<glob-mask>}. Если ни один файл в коммите не соответствует маске для указанной позиции, пуш отклоняется;
	\item post-receive --- выполняется после успешного приёма данных. Записывает хеши новых тегов в файл \texttt{push-tags}, а push-параметры --- в файл \texttt{push-options}. После завершения работы Git промежуточный слой читает эти файлы и вызывает обработчик \texttt{OnPush}.
\end{enumerate}

В \texttt{OnPush} мы читаем номер позиции из push-параметров и выполняем следующие действия:

\begin{enumerate}
	\item Читает номер позиции из push-опций.
	\item Если позиция больше 1, проверяет в базе данных, что предыдущее задание (позиция N-1) уже имеет сданную попытку. Последовательность обязательна: нельзя сдать задание 2, не сдав задание 1.
	\item Находит \texttt{TaskID} по номеру позиции в группе заданий.
	\item Регистрирует попытку: создаёт запись в таблице \texttt{attempts} и в таблице \texttt{attempt\_transitions} с указанием хеша коммита из тега и текущей даты.
\end{enumerate}

\subsection{Альтернативный сценарий: push через веб-интерфейс}

Система также поддерживает отправку решений через веб-интерфейс. Пользователь загружает ZIP-архив с файлами решения через маршрут \texttt{POST /attempts}. Сервер:

\begin{enumerate}
	\item Распаковывает архив во временную директорию.
	\item Если bare-репозиторий студента ещё не существует, инициализирует его из шаблона (если шаблон предусмотрен) или создаёт пустой.
	\item Клонирует bare-репозиторий во временную рабочую директорию.
	\item Записывает файлы, создаёт коммит от имени системного пользователя \texttt{mm-backend}.
	\item Выполняет push обратно в bare-репозиторий.
	\item Регистрирует попытку с хешем созданного коммита.
\end{enumerate}

Оба сценария записывают данные в один и тот же репозиторий и проходят одинаковую валидацию последовательности. Схема обоих сценариев показана на рисунке~\ref{fig:attempt-flow}.

\section{Комбинированная модель хранения}

Для хранения попыток используется комбинированная модель: Git отвечает за версионирование файлов, а реляционная база данных PostgreSQL --- за метаданные и состояние попыток.

\subsection{Хранение файлов в Git}

Каждый bare-репозиторий на диске содержит полную историю изменений файлов студента. Git, как было показано в разделе~\ref{sec:comparison}, предоставляет контентно-адресуемое хранилище: одинаковые файлы не дублируются, каждый коммит является полным слепком файлового дерева, а целостность данных проверяется через SHA-1 хеши. Репозиторий студента содержит все его попытки по всем заданиям данной группы --- каждая попытка представлена отдельным тегом, указывающим на соответствующий коммит.

Такой подход даёт несколько преимуществ:

\begin{itemize}
	\item эффективное хранение --- если студент меняет один файл из десяти, Git сохраняет только изменённый blob;
	\item встроенное версионирование --- история доступна через стандартные Git-команды (\texttt{git log});
	\item при необходимости студент может продолжать работать в своём репозитории между попытками, используя обычный порядок работы с Git.
\end{itemize}

\subsection{Хранение метаданных в PostgreSQL}

Метаданные попыток хранятся в двух связанных таблицах:

\begin{itemize}
	\item \texttt{attempts} --- связывает пользователя с заданием, содержит их идентификаторы;
	\item \texttt{attempt\_transitions} --- хранит историю состояний попытки: предыдущее и новое состояние (например, \texttt{submitted} $\to$ \texttt{graded}), временную метку и JSON-объект с дополнительными данными, включая хеш коммита.
\end{itemize}

Механизм гарантирует, что повторная отправка не перезаписывает предыдущую попытку, а создаёт новый переход. Хеш коммита, сохранённый в \path{transition_data}, связывает метаданные в PostgreSQL с содержимым в Git.

\subsection{Шаблоны решений}

Преподаватель может загрузить шаблон решения через маршрут \texttt{POST /tasks/\{id\}/template} в виде ZIP-архива. Сервер создаёт bare-репозиторий с содержимым архива. При первой отправке решения студентом (если шаблон существует) этот репозиторий клонируется и становится основой для репозитория студента. Если шаблон не предусмотрен, репозиторий студента инициализируется пустым.

\subsection{Сравнение версий}

\texttt{GET /attempts/diff} позволяет получить разницу между двумя попытками. Параметрами запроса передаются идентификаторы попыток. Сервер открывает bare-репозиторий, извлекает хеши коммитов из соответствующих записей \texttt{attempt\_transitions} и выполняет \texttt{git diff} между ними. Если задание определяет паттерны файлов (glob-маски), diff фильтруется --- показываются только изменения в файлах, соответствующих заданию. Это позволяет преподавателю видеть только релевантные изменения, игнорируя служебные файлы.

\conclusion

В ходе выполнения данной работы были решены следующие задачи:
\begin{itemize}
	\item проанализированы существующие подходы к хранению программного кода, выявлены преимущества систем контроля версий на базе Git;
	\item исследованы современные стандарты обмена данными между клиентом и сервером в контексте образовательной платформы;
	\item изучена роль протокола SSH в передаче данных через инструмент Git;
	\item спроектирован процесс взаимодействия студентов с подсистемой хранения решений через CLI-интерфейс и веб-версию платформы;
	\item реализованы механизмы аутентификации и авторизации с использованием SSH-ключей, а также управление доступом к репозиториям;
	\item внедрён механизм передачи метаданных в процесс git push для управления логикой приёма заданий;
	\item создана комбинированная модель хранения попыток, совмещающая Git для файлов и реляционную базу данных для метаданных.
\end{itemize}
