\intro

Современное высшее образование, особенно в области информационных технологий, находится в условиях активной трансформации. Вызвано это как нехваткой квалифицированных кадров на рынке труда, так и ростом числа желающих развиваться в этой сфере. На фоне развития отрасли, традиционные образовательные подходы и методики обучения теряют свою актуальность, становятся недостаточно эффективными в подготовке специалистов. Прежние стандартные системы не всегда способны обеспечить необходимую гибкость, интерактивность и практическую направленность, которые востребованы в условиях быстро меняющегося рынка.

Под влиянием данных факторов активно развиваются цифровые образовательные платформы. Они не только помогают в организации и структурировании учебных программ, но и облегчают повседневную работу как студентов, так и преподавателей, автоматизируя рутинные процессы и предоставляя современные инструменты для обучения. Одной из ключевых задач таких платформ --- организация процесса сдачи, хранения и проверки заданий.

Традиционные подходы к организации хранения студенческих работ --- будь то использование BLOB-объектов в базах данных или стандартных файловых систем, часто сталкиваются с определенными технологическими вызовами. В частности, при таких архитектурных решениях бывает непросто оптимизировать хранение информации, настроить гибкое версионирование. Это, в свою очередь, усложняет внедрение таких функций, как сравнение различных версий файлов, откат к предыдущим состояниям работы или детальный анализ метаданных по каждой попытке сдачи.

В индустрии информационных технологий для решения проблем версионирования, эффективного хранения проектов и организации совместной работы над ними широко применяются системы контроля версий (VCS), в частности Git. Освоение навыков работы с Git является фундаментальным требованием для будущих специалистов, поскольку этот инструмент является стандартом в современной разработке программного обеспечения. Интеграция Git в образовательный процесс, позволяющая студентам повседневно использовать его для сдачи и управления своими заданиями, способствует формированию профессиональных компетенций и облегчает их последующую адаптацию к требованиям быстро меняющегося рынка труда.

Целью данной работы является проектирование и реализация части образовательной платформы, которая использует Git для версионирования студенческих заданий, эффективного хранения данных, а также функционалом для удобной сдачи и проверки решений.

В ходе работы должны быть решены следующие задачи:
\begin{itemize}
	\item проанализировать существующие подходы к хранению программного кода, выявив преимущества систем контроля версий на базе Git;
	\item исследовать применение архитектуры REST API для построения основного сервера образовательной платформы;
	\item изучить принципы работы протокола SSH в обеспечении безопасного транспортного уровня для Git;
	\item разработать архитектуру Git-сервера;
	\item реализовать механизм аутентификации и авторизации с использованием SSH-ключей, а также управление доступом к репозиториям;
	\item внедрить механизм передачи метаданных в процесс git push для управления логикой приёма заданий;
	\item создать комбинированную модель хранения попыток, совмещающую Git для файлов и реляционную базу данных для метаданных.
\end{itemize}

\section{Архитектура REST API для построения основного сервера образовательной платформы}

REST (Representational State Transfer) --- архитектурный стиль для построения распределенных гипермедиа-систем, предложенный Роем Филдингом в 2000 году \cite{fielding2000architectural}. REST определяет набор ограничений, которые при совместном применении обеспечивают масштабируемость, производительность и простоту поддержки веб-сервисов.

REST оперирует концепцией ресурсов. Ресурс --- это любой объект, доступ к которому осуществляется через уникальный идентификатор (URL). Взаимодействие с ресурсами выполняется с помощью стандартных HTTP-методов: GET для получения, POST для создания, PUT для полного обновления, PATCH для частичного обновления, DELETE для удаления \cite{fielding2000architectural}.

Основные ограничения REST:

\begin{itemize}
	\item Клиент-сервер. Клиент и сервер разделены и общаются только через запросы и ответы. Это позволяет развивать их независимо.
	\item Отсутствие состояния. Каждый запрос содержит всю информацию, необходимую для его обработки. Сервер не хранит контекст между запросами. Это упрощает масштабирование и повышает отказоустойчивость \cite{fielding2000architectural}.
	\item Кеширование. Ответы сервера могут быть явно помечены как кешируемые. Клиенты и промежуточные узлы могут повторно использовать закешированные ответы, снижая нагрузку на сервер \cite{richardson2013restful}.
	\item Единообразие интерфейса. Все ресурсы идентифицируются через URL, а операции над ними выполняются стандартными HTTP-методами. Это делает API предсказуемым и упрощает интеграцию.
	\item Многоуровневая система. Между клиентом и сервером могут находиться промежуточные узлы (балансировщики, прокси). Каждый уровень видит только соседний, что упрощает архитектуру \cite{richardson2013restful}.
\end{itemize}

REST часто сравнивают с другими подходами. SOAP использует строгую типизацию и XML-схемы, но сложнее в реализации. RPC вызывает удаленные функции, но не стандартизирует работу с ресурсами. GraphQL позволяет клиенту запрашивать только нужные данные, но требует сложной схемы на сервере \cite{richardson2013restful}. REST проще SOAP, единообразнее RPC и использует стандартный HTTP без дополнительных протоколов.

\section{Сравнительный анализ подходов к хранению программного кода}

Чтобы оценить, насколько тот или иной подход годится для хранения версионированного кода, нужна система координат. В теории баз данных для этого есть ACID --- набор свойств, которым должна удовлетворять надёжная система \cite{haerder1983principles}. Сам термин ввели Тео Хардер и Андреас Ройтер в 1983 году \cite{haerder1983principles}, опираясь на работы Джима Грея по транзакциям \cite{gray1981transaction}. Расшифровывается так:

\begin{itemize}
	\item Atomicity (атомарность) --- операция выполняется целиком или не выполняется вовсе.
	\item Consistency (согласованность) --- система всегда остаётся в корректном состоянии; инварианты не нарушаются.
	\item Isolation (изоляция) --- параллельные операции не влияют друг на друга.
	\item Durability (долговечность) --- если данные сохранены, они переживают сбой.
\end{itemize}

Разберём три подхода к хранению кода, ориентируясь на ACID.

\subsection{Хранение файлов в реляционных СУБД (BLOB-объекты)}

BLOB (Binary Large Object) --- тип данных в реляционных СУБД для хранения бинарных данных \cite{garcia2009database}. Если хранить код в BLOB, каждая попытка --- строка в таблице с полем типа BLOB.

Проблема в том, что реляционная модель не рассчитана на версионирование древовидных структур. BLOB --- чёрный ящик для базы данных: она не знает, что внутри, и не может гарантировать согласованность содержимого. Consistency из ACID работает на уровне строки, но не на уровне структуры проекта \cite{postgresacid}.

Также, если задание состоит из нескольких файлов, нет атомарного обновления набора файлов как единого целого без дополнительной обвязки. Isolation могла бы давать изоляцию строк, но при конкурентной записи в BLOB возможны проблемы, описанные в документации PostgreSQL \cite{postgresacid}. Сравнение версий требует выгрузки BLOB-ов наружу, для чего не располагает база данных.

BLOB решает задачу «просто сохранить байты», но не решает задачу «хранить версионированный код с историей». ACID-гарантии, которые СУБД даёт для чисел и строк, почти не работают для этого сценария.

\subsection{Хранение файлов на файловой системе}

Второй подход --- хранить каждую версию как набор файлов в директории на диске.

С точки зрения ACID:

\begin{itemize}
	\item Atomicity --- операции FS не группируются в транзакции. При записи трёх файлов два могут записаться, третий --- нет \cite{tanenbaum2015modern}.
	\item Consistency --- никаких встроенных инвариантов. Можно случайно удалить половину файлов, и система этого не заметит.
	\item Isolation --- при конкурентном доступе возможны состояния гонки.
	\item Durability --- да, данные сохраняются на диск. Но это единственное свойство ACID, которое FS даёт (и то не всегда).
\end{itemize}

Плюс FS не хранит историю --- нельзя спросить «а что было до перезаписи?». Для этого нужна отдельная база данных, но тогда возникает проблема синхронизации между FS и этой БД. Файловая система --- удобный строительный блок, но не готовая система для хранения версий кода.

\subsection{Преимущества систем контроля версий на базе Git}

Git --- это распределенная система контроля версий, созданная Линусом Торвальдсом в 2005 году для разработки ядра Linux. Сегодня это стандартный инструмент для управления исходным кодом практически в любом IT-проекте \cite{chacon2014pro}.

В отличие от многих других систем, Git не хранит списки изменений между версиями. Вместо этого Git хранит полные слепки (snapshots) файлового дерева на каждый момент коммита. Такая схема хранения оказывается эффективнее за счет переиспользования неизмененных объектов.

В основе Git лежит \quot{контентно-адресуемое хранилище} (content-addressable storage). Фактически Git --- это база данных ключ-значение, где ключом является SHA-1 хеш содержимого, а значением --- сами данные \cite{chacon2014pro}\cite{aosagit}. Git использует четыре типа объектов:

\begin{itemize}
	\item Blob --- содержимое файла. У blob-объекта нет имени файла, это просто набор байт. Если два разных файла имеют одинаковое содержимое, они будут ссылаться на один и тот же blob. Это позволяет избегать дублирования информации.
	\item Tree --- аналог директории. Содержит список записей вида \quot{имя файла --- ссылка на blob} или \quot{имя поддиректории --- ссылка на другой tree}.
	\item Commit --- ссылается на корневой tree (полный слепок репозитория), на ноль или более родительских коммитов, а также хранит метаданные: автор, дата, сообщение.
	\item Tag --- именованная ссылка на коммит, обычно для обозначения версий.
\end{itemize}

Git позволяет экономить место на диске. При создании нового \quot{коммита}, Git не копирует все файлы заново. Вместо этого он создает новые blob-объекты только для измененных файлов. Файлы, которые не менялись, продолжают ссылаться на уже существующие объекты \cite{gitchaconobjects}. Например, если в проекте из 100 файлов изменился один, Git создаст один новый blob, новый tree (для директории с измененным файлом) и новый commit. Остальные 99 файлов останутся на своих старых blob-объектах. Получается, что каждый коммит --- это полноценный снимок всего репрозитория, но занимает он места ровно столько, сколько нужно для описания изменений.

Со временем Git дополнительно упаковывает объекты в pack-файлы, используя дельта-компрессию (метод сжатия данных, при котором сохраняются не сами исходные данные, а разница между текущим и предыдущим значением) внутри каждого pack-файла \cite{aosagit}. Похожие объекты сжимаются относительно друг друга, что еще сильнее уменьшает объем хранимых данных.

Каждый объект в Git идентифицируется SHA-1 хешем содержимого. Если байт в объекте изменится, хеш перестанет соответствовать, и Git обнаружит повреждение \cite{chacon2014pro}.

Коммиты в Git образуют направленный ациклический граф (DAG) \cite{aosagit}. Каждый коммит ссылается на родительские коммиты, что позволяет восстановить полную историю изменений. Ветвление --- создание нового указателя на коммит. Ветки в Git --- легковесные ссылки, которые создаются и удаляются за миллисекунды.

Если посмотреть на Git через призму ACID, он неожиданно хорошо закрывает почти все свойства. Consistency даёт контентно-адресуемое хранилище: SHA-1 хеш содержимого --- это инвариант, любое повреждение данных обнаруживается \cite{chacon2014pro}. Atomicity --- коммит либо применяется целиком, либо нет; частичного коммита не бывает. Isolation обеспечивается ветками: изменения в одной ветке не видны в другой до явного слияния. Durability --- каждый клон репозитория является полной копией данных \cite{chacon2014pro}. Git не проектировался как ACID-система, но для задачи хранения версионированного кода он даёт гарантии, близкие к ACID.

\section{Принципы работы протокола SSH}

SSH (Secure Shell) --- протокол безопасного удаленного доступа к серверам. Разработан в 1995 году финской компанией SSH Communications Security как замена небезопасным протоколам Telnet и rsh, которые передавали данные (включая пароли) в открытом виде \cite{rfc4251}.

Основная проблема, которую решает SSH: как двум компьютерам общаться по незащищенному каналу (Интернету) так, чтобы никто не мог перехватить, прочитать или подменить передаваемые данные?

Архитектура SSH (RFC 4251) состоит из трех уровней и первый из них --- транспортный протокол (RFC 4253). Этот уровень работает поверх TCP и отвечает за установление защищенного соединения. Сначала сервер предъявляет свой host-ключ --- клиент проверяет, что он подключился именно к тому серверу, к которому собирался. Затем стороны выполняют обмен ключами по протоколу Диффи-Хеллмана, в результате которого получают общий секретный ключ. После этого весь трафик шифруется симметричным шифром (например, AES). Важная особенность --- \quot{perfect forward secrecy}: даже если злоумышленник когда-нибудь узнает долговременный секретный ключ сервера, он не сможет расшифровать ранее перехваченные сессии \cite{rfc4253}.

После установки защищенного канала сервер проверяет подлинность клиента. Основные методы:
\begin{itemize}
	\item Пароль --- классический способ, но пароль передается внутри защищенного канала.
	\item Публичный ключ --- клиент доказывает, что владеет приватным ключом, соответствующим публичному ключу, который известен серверу.
	\item Keyboard-interactive --- сервер задает клиенту вопросы (например, одноразовый пароль из SMS).
\end{itemize}

Аутентификация по публичному ключу --- способ, удобный для автоматизированных сценариев. Пользователь генерирует пару ключей: приватный (хранится только у владельца) и публичный (можно свободно распространять). Публичный ключ добавляется на сервер. При подключении SSH использует криптографию с открытым ключом: сервер отправляет случайное число и просит подписать его приватным ключом. Если подпись верна --- клиент доказал, что владеет приватным ключом, и аутентификация проходит успешно.

После аутентификации протокол соединения мультиплексирует несколько логических каналов внутри одного SSH-соединения. Через одно соединение можно одновременно передавать файлы, запускать несколько команд, пересылать порты.

Для использования SSH с Git не требуется стандартный OpenSSH-демон. Можно реализовать собственный SSH-сервер, который будет принимать подключения, проверять аутентификацию по ключам и выполнять нужные команды. Это дает возможность интегрировать аутентификацию с произвольным хранилищем данных --- например, проверять ключи через базу данных, а не через системные файлы authorized\_keys. Такой подход упрощает управление ключами и позволяет реализовать механизмы добавления и удаления ключей через API.

\section{Протокол Git Wire и его функционирование поверх SSH}

Когда разработчик выполняет \texttt{git push} или \texttt{git pull}, Git-клиент и Git-сервер обмениваются данными по определенному протоколу --- Git Wire Protocol \cite{gitprotocolpack}. Этот протокол определяет, как клиент и сервер договариваются о том, какие данные нужно передать, и как эти данные упаковываются в pack-файлы.

В Git существует два основных сценария передачи данных.

Клиент хочет получить данные с сервера. На сервере запускается процесс \texttt{git-upload-pack}, на клиенте --- \texttt{git-fetch-pack}. Последовательность шагов:
\begin{enumerate}
	\item Клиент подключается к серверу и запрашивает \texttt{git-upload-pack}.
	\item Сервер отправляет список ссылок (refs): какие ветки существуют и на какие коммиты они указывают.
	\item Клиент сообщает серверу, какие коммиты у него уже есть.
	\item Сервер вычисляет, каких объектов не хватает клиенту, упаковывает их в pack-файл и отправляет.
\end{enumerate}

Клиент хочет отправить данные на сервер. На сервере запускается \texttt{git-receive-pack}, на клиенте --- \texttt{git-send-pack}:
\begin{enumerate}
	\item Клиент подключается к серверу и запрашивает \texttt{git-receive-pack}.
	\item Сервер отправляет текущие ссылки.
	\item Клиент сообщает, какие ссылки он хочет обновить и какие новые объекты (коммиты, blob-ы) для этого нужны.
	\item Сервер проверяет, можно ли выполнить обновление (fast-forward?).
	\item Клиент упаковывает новые объекты в pack-файл и отправляет.
	\item Сервер принимает данные и обновляет ссылки.
	\item После успешного приема данных выполняются post-receive хуки.
\end{enumerate}

SSH-транспорт --- самый простой с точки зрения реализации: клиент запускает на сервере нужную команду через SSH и общается с ней через stdin/stdout \cite{gitprotocolpack}. Фактически, выполнение \texttt{git push ssh://server/repo} эквивалентно выполнению на сервере команды:

\texttt{ssh server "git-receive-pack '/repo.git'"}

После запуска процесса Git-клиент и Git-сервер общаются напрямую через stdin/stdout, а SSH обеспечивает шифрование и аутентификацию.

Важная возможность Git-протокола --- push-опции (push options). Git позволяет передавать дополнительные параметры при push через флаг \texttt{-o} или \texttt{--push-option} \cite{gitprotocolpack}. Когда клиент отправляет push-опции, они передаются серверному процессу и могут быть обработаны post-receive хуком \cite{githooks}.

Post-receive хук --- это скрипт, который выполняется после успешного приема данных. Он запускается в контексте Git-репозитория и может читать push-опции из переменных окружения. Хуки --- стандартный механизм Git, позволяющий добавлять произвольную логику на стороне сервера без модификации самого Git \cite{githooks}.

Сравнение SSH и HTTPS в контексте Git показывает, что у каждого транспорта есть свои особенности. HTTPS требует настройки веб-сервера и дополнительной аутентификации (базовый HTTP Auth или cookie). SSH предоставляет аутентификацию и шифрование \quot{из коробки}: достаточно добавить публичный ключ на сервер. SSH-сервер может работать независимо от основного HTTP-сервера, что упрощает разделение трафика \cite{chacon2014pro}.
